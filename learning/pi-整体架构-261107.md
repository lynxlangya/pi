# pi 整体架构（先看全局，再读代码）

> 读 [阅读顺序](./pi-ai-阅读顺序-261107.md) 和 [调试指南](./pi-ai-调试指南-261107.md) 之前先读这篇。目的是先知道每段代码在整个系统里是干什么的，再去看细节。

## 一句话

pi 有两条产品线，最后都调用同一个底座 **pi-ai**。pi-ai 只做一件事：用同一套接口调用各家大模型。

## 第一层：整个仓库

```
   pi-coding-agent              apps/p2
   终端里的 pi 命令             Web 版应用（实验原型）
          │                         │
          ▼                         ▼
   pi-agent-core                pi-durable
   Agent 循环 + 工具调用        能断点续跑的长任务
          │                         │
          └──────────┬──────────────┘
                     ▼
                   pi-ai          ← 阶段 1 学的就是这一层
          用同一套接口调用各家大模型
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
      pi-schema            pi-telemetry
  工具参数的 JSON Schema    指标和链路追踪
```

| 包 | 做什么 | 依赖 |
| --- | --- | --- |
| `pi-ai` | 统一的大模型 API：模型目录、认证、各家协议适配 | schema、telemetry |
| `pi-agent-core` | 通用 Agent：循环调用模型、执行工具、管理状态 | pi-ai、schema |
| `pi-coding-agent` | 编程 Agent 命令行（read/bash/edit/write 工具 + 会话管理） | agent-core、pi-ai、tui、mcp、codemode |
| `pi-durable` | 可持久化的对话、任务和文档运行时：进程挂了能接着跑 | chord、pi-ai、codemode、schema、telemetry |
| `chord` | 跨进程的对象运行时（契约、存储、插件热加载、HTTP、worker） | schema、telemetry |
| `pi-env` | pi-durable 的远程执行环境：通过 SSH 部署的小守护进程 | chord、durable |
| `pi-codemode` | 沙箱里执行 JavaScript，只能调用注入的工具 | 无 |
| `pi-mcp` | 独立的 MCP 客户端 | 无 |
| `pi-tui` | 终端界面库 | 无 |
| `pi-schema` / `pi-telemetry` | 基础设施：JSON Schema 校验 / 遥测契约 | 无 |

两条线的区别：

- **经典线**（coding-agent → agent-core）：单进程，会话结束就结束。适合先学 Agent 循环最基本的形态。
- **新线**（durable + chord）：任务能持久化、恢复、跨进程运行。做给客户的长任务系统，最终要看这一层。
- `apps/p2` 的 README 写明它是**实验原型，很快会被移除**。可以拿来参考 durable 怎么用，但不要在它上面做东西。

## 第二层：pi-ai 内部

一次调用从上往下走 3 层，最后得到一个事件流：

```
调用方  models.streamSimple(model, context)
   │
   ▼
Models        models.ts          找 provider，解析认证，合并请求头
   │
   ▼
Provider      providers/*.ts     一份配置：有哪些模型 + key 从哪读 + 用哪种协议
   │                             （DeepSeek 的整个 provider 只有 15 行）
   ▼
Api 实现      api/*.ts           翻译成各家的 HTTP 协议，解析流式响应 ──→ 公共工具 utils/
   │                                                                     · 换模型时清洗历史
   ▼                                                                     · 失败重试
事件流        AssistantMessageEventStream                                · 上下文超长判断
              start → 增量 → done 或 error                               · token 用量估算
```

三个要点：

1. **Provider 不写逻辑，只做配置。** 接入一家新的 OpenAI 兼容服务（比如公司内部网关），复制一个 provider 文件，改 id、baseUrl、key 和模型清单就行，不用写协议代码。
2. **Api 实现按协议分，不按厂商分。** DeepSeek、Groq、OpenRouter 等都走 `openai-completions`，各家的差别由兼容层（compat）处理。全仓库大约 10 种协议，读懂 `openai-completions` 一种就够了。
3. **错误不抛异常，而是放进事件流。** 调用方永远拿到一个流，失败时会收到 `error` 事件，最终消息的 `stopReason` 是 `error` 或 `aborted`。

## 阶段 1 的主干：只读这 3 个函数

| 顺序 | 函数 | 回答什么问题 |
| --- | --- | --- |
| 1 | [Models.streamSimple](../packages/ai/src/models.ts:1084) | 请求从哪进来？为什么调用之后立刻返回？ |
| 2 | [applyAuth](../packages/ai/src/models.ts:988) | key 从哪来？请求头按什么顺序合并？ |
| 3 | [openai-completions 的 stream](../packages/ai/src/api/openai-completions.ts:330) | 请求怎么拼出来？流式响应怎么变成事件？ |

读主干时碰到下面这些，先当黑盒跳过，用到时再查：

- `utils/` 下的公共工具（清洗、重试、超长、估算、流式 JSON）
- 另外 9 种协议实现（anthropic、google、bedrock……）
- OAuth、凭据存储、模型列表动态刷新
- compat 里 DeepSeek 以外各家的分支

读完主干后的检验：调用 DeepSeek 时，你能说出请求经过了哪几个函数，出错时该去哪一层查。

## 和后续阶段的关系

- 你以后要做的 Agent 系统，核心在 **agent-core（Agent 循环）** 或 **durable（长任务持久化）**。pi-ai 是它们调用的底座。
- 所以 pi-ai 的目标是：能把它当黑盒用，出问题时知道去哪一层查。不需要每个分支都弄懂。
- 主干读通之后，再按 [阅读顺序](./pi-ai-阅读顺序-261107.md) 选读感兴趣的部分，用 [调试指南](./pi-ai-调试指南-261107.md) 验证自己的理解。
